## Статус

2026-10-04 независимо разобраны журнал и USBPcap внешнего CLI-прогона
17.01.0516 -> 17.02.0501. Это продолжение исследований в `m_flasher`,
не интеграция внешнего writer и не новая live-прошивка.
Данные анализировались локально; firmware восстановлены для потокового
хеширования, не записаны на диск.

[Общий проект m4_cli_flasher](https://github.com/kewl-ua/m4_cli_flasher)
используется как справочный источник описания протокола и реализации.
Его README прочитан; код и тесты не аудированы и не переносились.
Ревизия кода, реально запущенного при записи capture, не установлена.
Заявления проекта не заменяют приведенные ниже независимые измерения.

## Файлы: теперь проверен raw-поток, не только file-sent

Повторно использован метод USBPcap reassembly и CRC из
[первого отчета](./capture-transfer.md#метод-проверки).

- 23 файла, **665796192 bytes**.
- 679445 исходящих DUML `00/2A`: 23 open, **679399 data**, 23 finish.
- Индексы data chunks непрерывны внутри каждого файла; повторной отправки
  chunks в восстановленной последовательности не найдено.
- Все declared sizes и finish MD5 совпали с восстановленным содержимым.
- Config побайтно совпал с config нашего ZIP 17.02.0501.
- Все 23 файла совпали по имени, порядку, размеру, MD5, SHA256 и числу
  chunks с независимо разобранным offline capture Assistant, ранее
  сопоставленным с ZIP. Таким образом проверены именно bytes файлов.

Первая open: epoch `1791133574.592058`; последняя исходящая finish:
`1791133637.986472`. **File-transfer interval = 63.394414 s**.
Сумма округленных `seconds` в 23 `file-sent` — 63.4 s.
Опубликованные 64.5 s не воспроизвелись для этих границ;
это различие измерений, не свидетельство ошибки передачи.
От `flash-begin` до отправки `85` прошло 64.701055 s.

Совпадение files не доказывает полное равенство всех кадров/таймингов
Assistant и CLI. Полная побайтовая parity всех control/data payload
отдельным сравнением двух потоков здесь не проверялась.

## ACK и границы полноты

В raw capture 668 ответов `00/2A`: 23 open, **622 data ACK**, 23 finish.
Data ACK содержат `00` + LE index. Индексы не убывают внутри файла,
последний равен последнему chunk каждого из 23 файлов.

Их собственный DUML sequence идет от 0 до 625, но отсутствуют
**98, 241, 242, 500**:

| Frame до / после | Sequence до / после |
|---|---|
| 103988 / 104414 | 97 / 99 |
| 254548 / 255808 | 240 / 243 |
| 551522 / 552204 | 499 / 501 |

Проверка непрерывности ACK sequence, проходившая на двух captures Assistant,
здесь не проходит. Причина пропусков не установлена: нельзя приписывать
их устройству, capture, драйверу или журналированию без дополнительной
проверки. Полное восстановление firmware и финальные ACK при этом успешны.
Правило «всегда непрерывный ACK sequence» не является доказанным контрактом.

Четыре truncated USB records: 693097/693109 на address 8,
701647/701653 на address 10; endpoint 83, captured 65535 / original 65563.
Они не относятся к file transfer OUT 04 / IN 85.
На IN 85 старых addresses 6 и 8 остались по 3 неразобранных bytes;
на address 10 хвоста нет. OUT 04 собран без хвостов для всех трех адресов.
Принятые DUML packets прошли CRC, но полнота capture всех сообщений
и назначение остаточных bytes не заявляются.

## Журнал и wire-подтверждение результата

Все **1139 сохраненных кадров** журнала (70 tx, 1069 rx)
прошли проверку framing, CRC8 и CRC16.
275 записанных control/status/version packets сопоставлены с raw capture
по route, flags, sequence и payload.

Время ниже относительно `flash-begin`; данные взяты из USB capture.

В `00/01` slice bytes 22..25 дает начальную 17.01.0516 и конечную
17.02.0501: для этих ответов последние два bytes задают major/minor,
первые два — LE число build (`04 02` = 516, `f5 01` = 501).
Это не формат четырех независимых decimal bytes ответа `4F`.
Начальная версия подтверждена wire-ответом, а не только expected_current.
Таким образом это именно смена версии, не еще один Refresh.

## Два reconnect и статусы

Исторические USB addresses: **6 -> 8 -> 10**, bus 1.
Журнал содержит два `link-lost`, 14 `reconnect-wait`, два `reconnected`
с длительностями 14.1 и 14.2 s; `greet-failed` в нем нет.
Это результаты открытия transport приложением, не точные длительности reboot.

| Address | Число `42` | Первый / последний prefix payload |
|---:|---:|---|
| 6 | 112 | `03 03 00` / `03 49 12` |
| 8 | 134 | `03 49 00` / `03 57 00` |
| 10 | 5 | `03 57 00` / `04 01 00` |

Всего 251 status: 44 коротких (3 bytes), 89 длиной 147,
118 длиной 155. Для всех 207 длинных вновь выполнено
`length = 3 + 8 * payload[2]`. Это структурная проверка,
не полный decoder состояний всех компонентов.
Последние пять payload: `03 57 00`, `03 57 00`, `03 64 00`,
`03 64 00`, `04 01 00`; terminal имеет sequence 4, не 2.
Нельзя жестко ожидать ровно три финальных packets или конкретный sequence.

## Вывод и следующий этап

Самостоятельная смена 17.01.0516 -> 17.02.0501 теперь подтверждена
не только внешним описанием, но и независимым восстановлением файлов,
terminal и конечной версии из USB capture, согласованных с журналом.
Это конкретный Windows-прогон одного M4T с одним target ZIP.

Открыты Linux transport, интеграция в текущий SDK, проверка signatures,
полная семантика статусов, applicability hardware variants, ошибки/recovery.
Следующие вопросы для offline-исследования: пропуски ACK, pacing/window,
идентификация устройства после reconnect и проверка реализации автомата.
Никакие новые команды устройству этой проверкой не отправлялись.
