## Уровни доказательств

| Утверждение | Основание | Что проверено / ограничение |
|---|---|---|
| Процедура и цель | `flash-begin` | `upgrade-center`, target и expected_current = 17.02.0501, `verified=false` |
| Начальная версия | `device` и сохраненный ответ | `WA345T AC Ver.A`, firmware bytes `f5 01 02 11`; Refresh той же версии |
| Корректность записанных кадров | 511 `tx` + 1933 `rx` | Все 2444 кадра прошли length/version, CRC8 и CRC16 |
| Передача состава пакета | 23 `file-sent` | Имена, порядок, sizes, MD5 и chunks совпали с результатами независимого разбора offline capture Assistant |
| Фактические file-data bytes этого прогона | В JSONL отсутствуют data chunks | Не восстановлены из журнала; нужен отдельный raw USBPcap |
| Complete / Success | Сохраненный `rx` от `48`, `00/42` | Payload `04 01 00`; согласуется с публичной схемой и captures Assistant |
| Версия после завершения | Коррелируемый `4F`, затем `1F/00/01` | Оба ответа согласуются с 17.02.0501; подтверждение не ограничено записью `ok=true` |
| Assistant закрыт, использован native Windows backend | Описание внешнего прогона | Состояние процессов и реализация backend этой проверкой не подтверждались |
| Linux/macOS, смена версии, recovery при ошибке | Этот журнал | Не проверены |

CRC подтверждает целостность сохраненных кадров, но не аутентичность
журнала и не заменяет независимый USB capture.
В частности, для Refresh совпадение начальной и конечной версии само
по себе не доказывает переустановку; важен terminal status устройства.
Проверка работоспособности всех компонентов после обновления не выполнялась.

## Передача и счетчики

Сумма 23 `file-sent`: **665796192 bytes**, **679399 data chunks**.
Config `wa345t.cfg.sig` имеет MD5 `7f7857ab44e5c086b17f6b5215a8d353`.
Состав и порядок совпадают с
[Offline Upgrade 17.02.0501](./capture-offline-upgrade.md),
включая hardware variants.

В журнале сохранены 23 open и 23 finish requests, ответы:
23 open, 958 data ACK, 23 finish. **Данные chunks не сохранены**:
`file-sent` — отчет приложения, а не независимое восстановление потока.
Поэтому нельзя объявлять все отправленные firmware bytes проверенными
по этому JSONL, даже при совпавших MD5 в отчетах.

От первой open до последней исходящей finish — **96.981 s**.
Это интервал file transfer, не всей установки.
Полный интервал журнала — **205.026 s**.

## Хронология по записанным кадрам

Время относительно `flash-begin`, округлено до миллисекунд.
Адреса и payload — hex, sequence в таблице — decimal.
Ответы `83/84/85/4F/41` имеют обратные адреса и совпавший sequence.

`f5 01 02 11`. Нельзя подставлять decoder одной команды в другую.

## Что этот прогон уточняет

1. **Есть свидетельство самостоятельного успешного Refresh на Windows.**
   Оно сильнее одного сообщения приложения: журнал содержит terminal
   устройства и post-reconnect ответы версии.
2. **`06` на `85` снова сопровождается успешным завершением.**
   Это не универсальный decoder всех ненулевых ответов команды.
3. **Получение ответа `51` от `68` не оказалось обязательным для
   завершения этого прогона.** Сам запрос был отправлен; отсюда нельзя
   заключать, что его можно безусловно удалить из приветствия.
4. **Нули в `1F` могут быть временными после reconnect.**
   Здесь после двух нулевых результатов получена реальная версия.
   Универсальный timeout и причина нулевого значения не установлены.
5. **Не все этапы обязаны иметь тот же timing, что Assistant.**
   Внешний writer запросил `41` после ответа `4F`; в captures Assistant
   запрос `41` шел до этого ответа. Этот прогон завершился успешно.
6. **`0802` в текстовом логе не равно автоматически XML module id 0802.**
   Raw address `48` раскладывается в type 8 / index 2; форматтер пишет
   `0802`. Физический компонент или связь с WA345T_E2 этим не доказаны.

## Открытые проверки и документационные расхождения

Внешний `duml.md` прочитан как описание, а не принят целиком за
независимо подтвержденную спецификацию:

- Раздел гарантий смешивает `legacy-ftp` (`0A`, статусы от `1F`) и
  `upgrade-center` (`85`, статусы от `48`); гарантии нужно разделять
  при дальнейшей проверке реализации.
- Начальная формулировка о записи всей телеметрии расходится с описанием
  агрегированных счетчиков. В этом журнале 22 `rx-counted`; наличие
  части сырых telemetry frames не означает сохранение всего потока.
- Работа на Linux/macOS не подтверждена Windows-журналом.
- Окно 1250 chunks, универсальное число reboot, обязательность каждого
  приветствия и полная семантика расширенных `42` этим анализом не проверены.
- Из `verified=false` нельзя выводить готовность процедуры для всех M4T.
  Смена версии и обработка неуспешного прогона здесь не испытаны.

Следующие независимые этапы:

1. Разобрать заявленный `C:\dev\captures\ours_usb.pcap`: восстановить все
   файлы, проверить hashes, pacing и сопоставить финал с JSONL.
2. Проверить реализацию и тесты внешнего writer, зафиксировав ревизию;
   различать mock/parity tests и live-результаты.
3. Отдельно согласовать и проверить смену версии, reconnect identity,
   ошибки/recovery и Linux transport. Этот отчет не разрешает новые
   live-запросы или запись firmware.

Сырые журналы, capture, firmware и внешняя реализация в этот репозиторий
не добавлялись. Текущий SDK и его unit-тесты не изменены.
