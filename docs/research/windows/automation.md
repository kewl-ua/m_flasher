# Windows: адресный ввод, file picker и отдельный desktop

[Главная и карта документации](../../../README.md) | [Карта документации](../../README.md)

Экспериментальные способы автоматизации и их ограничения. Отрицательные и предварительные результаты сохранены; они не являются обещанием готовой автономности.

Материалы ниже сохраняют ход исследования. Последующие записи могут уточнять ранние гипотезы; ограничения приведены рядом с результатами.

## Режим без физического ввода (экспериментальный)

`DJIAssistant.connect(title=..., allow_physical_input=False)` и
`DJIAssistant.launch(executable, title=..., allow_physical_input=False)`
запрещают SDK вызывать set_focus/click_input для карточки, файлового поля
и fallback навигации Firmware Update. Для совместимости значение по
умолчанию True сохраняет ранее проверенные физические клики.
CLI: `dji-assistant --no-physical-input current` или
`dji-assistant --no-physical-input offline-select <package.zip>`.
Опция не поддерживается старым подробным firmware-probe.

На стартовой карточке пробуется LegacyIAccessible default action, только
если оно заявлено; файловое поле вызывается через Invoke. Если диалог
не появился, физического fallback нет: SDK сообщает ошибку. Уже выбранный
точный пакет может использоваться без открытия нового picker.

Это запрет ввода со стороны SDK, НЕ изоляция Windows desktop: сам запуск
Assistant или native modal может менять активное окно. Не доказано, что
приложение сохраняет чужой фокус. Живые ограничения Enterprise V2.1.20:
текст карточки Matrice 4T имеет пустой Legacy DefaultAction, поэтому
программное открытие карточки этим способом недоступно. У файлового поля
Invoke и отдельная экспериментальная Legacy DoDefaultAction не открыли
picker. Режим корректно остановился на карточке без физического клика;
фоновый startup-to-offline end-to-end пока не реализован.

Повторная live-проверка без взаимодействия пользователя с мышью/клавиатурой
2026-10-04 подтвердила ограничение: после нового запуска карточка найдена,
но отдельный экспериментальный Legacy DoDefaultAction даже при пустом
DefaultAction не открыл устройство за 5 с. Фокус и курсор не изменились.
Явное переключение на физический ввод позволило открыть тот же Matrice 4T.
На странице Offline Upgrade отдельно проверены Invoke и Legacy
DoDefaultAction поля: после каждого ожидания 6 с owned picker отсутствовал,
фокус и курсор не изменились. Возврат на Firmware Update выполнен через Invoke,
Current 17.02.0501 подтвержден; новые прошивки не запускались.
Таким образом, отсутствие программного перехода воспроизведено без
конкурирующего пользовательского ввода; причиной нельзя считать движение мыши.

## Адресные сообщения Chromium (экспериментальный режим)

```python
dji = DJIAssistant.connect(
    title="DJI Assistant 2 (Enterprise Series)",
    allow_physical_input=False,
    addressed_input=True,
)
dji.open_device("Matrice 4T")
dji.offline.select_package(r"C:\dev\fw_list\m4t\M4T_UAV_17.02.05.01_pro.zip")
```

Параметры также поддерживает `launch()`. CLI:
`dji-assistant --no-physical-input --addressed-input offline-select <package.zip>`.
По умолчанию режим выключен. Включение заменяет клики карточки и файлового
поля на одну последовательность WM_MOUSEMOVE/WM_LBUTTONDOWN/WM_LBUTTONUP,
адресованную конкретному Chrome_RenderWidgetHostHWND. SDK проверяет
единственность renderer, root HWND, PID, видимость и границы UIA-цели;
ScreenToClient преобразует координаты, SendMessageTimeout ограничивает ожидание.
Глобальный курсор не перемещается кодом SDK, set_focus не вызывается.
Если отправка не удалась, повторов и физического fallback нет.
Кнопки записи прошивки по-прежнему используют только guarded UIA Invoke.

Live-проверка 2026-10-04: после нового запуска SDK открыл Matrice 4T
с allow_physical_input=False/addressed_input=True, фокус и курсор сохранились.
Из пустого поля SDK открыл picker, выбрал официальный ZIP и проверил путь.
Итоговый фокус совпал с исходным, но в этом прогоне положение курсора изменилось:
причина изменения не установлена. Дополнительный замер каждого шага показал,
что открытие native picker меняет foreground HWND, затем Open Invoke возвращает
его основному окну; курсор оставался неизменным на всех трех шагах
(открытие, SetValue, Open Invoke). Полную изоляцию и сохранение фокуса
другого приложения эти проверки не доказывают. Это не headless/отдельный desktop.
Финально подтверждены Current 17.02.0501 и idle, новых прошивок не выполнялось.

## Прямая запись пути без picker

Live-проверка 2026-10-04 после нового запуска и открытия пустой offline-формы:
ValuePattern доступен, CurrentIsReadOnly=0, но вызов SetValue с полным путем
официального ZIP возвращает HRESULT 0x80004001 (E_NOTIMPL).
Последующее независимое чтение подтвердило пустое поле и отсутствие owned
file picker. Следовательно, заявленная доступность ValuePattern и отсутствие
read-only флага не доказывают поддержку записи; direct-path выбор пакета
через этот интерфейс не работает в проверенной Enterprise V2.1.20.
Start Upgrade был enabled даже до заполнения поля, поэтому состояние кнопки
тоже не доказывает загрузку пакета. После эксперимента SDK вернулся на
Firmware Update: Current 17.02.0501, idle. Start Upgrade/Start Update
не вызывались; прошивка не запускалась. Этот способ не включен в SDK.

## Исследование точки перехвата выбора файла

Read-only анализ установленного ASAR 2026-10-04 (без извлечения/изменения
файлов DJI и без инъекции) выявил Electron remote.dialog.showOpenDialog:
общий helper getPath вызывает getPathExtra, тот передает текущее окно,
параметры выбора и callback в showOpenDialog. Callback helper преобразует
массив выбранных путей в один путь для обычного выбора.

В aircraft bundle общий файловый компонент после callback меняет значение
модели и вызывает обработчик change. Отдельный offline-компонент имеет
readonly HTML input, модель dirPath и selectDir, который присваивает путь
из helper callback; далее firmware_dir_path передается в запрос обновления.
Это статические сведения о bundle с несколькими устройствами, НЕ доказательство
точного runtime-компонента текущего M4T. Связь с активной формой еще не проверена.
Readonly в HTML также не соответствует заявленному UIA IsReadOnly=0.

Кандидат для узкого экспериментального JS-перехвата: однократный возврат
валидированного массива путей через штатный callback showOpenDialog,
с обязательной проверкой активного компонента, типа openFile, версии
приложения и восстановлением исходной функции. Это пока гипотеза,
не реализованный адаптер и не подтвержденный выбор пакета без диалога.
Перехват глобальных Win32 файловых API/DLL не выбран: обнаружена более
высокоуровневая точка, но способ доступа к живому JS-контексту еще не найден.
У текущих DJIBrowser процессов не обнаружен TCP listener; в командных
строках отсутствует remote-debugging-port. Автооткрытие DevTools в main
закомментировано. Не следует считать открытый канал исполнения JS доступным.

Идентификатор проверенного установленного app.asar:
SHA256 `fd9cd1857b2fcec4ed19d71a189d7216390dfda606e8b08358843194ea76c28d`.
Хук не установлен, состояние модели не менялось, кнопки прошивки
не нажимались. Перед любым будущим runtime-прототипом требуется подтвердить
idle и исключить активную firmware-операцию.

Следующее read-only исследование уточнило активную страницу: LegacyIAccessible
Value документа содержит URL `app.asar/m210.html#/upgrade-offline`.
Несмотря на имя m210, UIA страницы идентифицирует подключенный Matrice 4T.
HTML этой страницы подключает utils, ws/ws-v2 и build/m210.js; в этом bundle
также найдены offline-обработчик выбора openFile и firmware_dir_path.
Это подтверждает нужный bundle/route, но живой экземпляр JS-компонента
и цепочка вызовов при выборе пакета пока не прочитаны.

DJIBrowser сообщает Electron 0.36.7. Статический bootstrap содержит
toggledevtools accelerator в debug-menu, но у действующего Windows окна
HMENU=0; существование строк debug-menu не доказывает доступность меню.
Один экспериментальный адресный F12 основному окну не создал видимых DevTools
или нового UIA Document; фокус и курсор сохранились. Это не доказательство
полного отсутствия DevTools, только отрицательный результат конкретной пробы.
Запуск debug-сборки/remote debugging, JS-перехват и DLL-инъекция не выполнялись.

После отдельного согласования проверен debugging runtime на изолированном
пустом окне того же DJIBrowser/Electron 0.36.7: временный JS-bootstrap вызвал
app.commandLine.appendSwitch для remote-debugging-address=127.0.0.1 и
remote-debugging-port=19347 до ready. Listener реально найден только на
127.0.0.1:19347 с PID тестового процесса; локальный /json/list вернул
страницу-заглушку и WebSocketDebuggerUrl. Тест не загружал DJI main/bundles,
не соединялся с устройством и не доказывает возможность перехвата живой
offline-формы. Окно штатно закрыто, исчезновение listener проверено.
Временный bootstrap удален. Установленные файлы DJI не изменены.
Это подтверждает возможность CDP-канала у runtime, но интеграция запуска
реального Assistant вместе с его сервисами и runtime JS-хук еще не реализованы.

Исследование штатной цепочки запуска: установленный main.js не запускает
DJIService/DJIServiceCore (в нем нет child_process/spawn); реальные процессы
показывают родительскую цепочку DJIService -> DJIBrowser. В frontend
ws-v2 обнаружены localhost endpoints 19870 и 19871. Поэтому успешный запуск
пустого Electron bootstrap не заменяет запуск всего Assistant: отдельный
renderer без сервисов может остаться в Waiting for Backend.
В строках DJIService найдены пути DJIBrowser/DJIApp и --debugger, но
контракт аргумента --debugger и его связь с Chromium debugging не установлены.
Этот аргумент не запускался. Подмены бинарников, изменения установленных
путей, повторного подключения второго frontend и DLL-инъекции не выполнялось.

Два live-запуска официального launcher с
`--remote-debugging-address=127.0.0.1 --remote-debugging-port=19347`
не передали эти аргументы DJIBrowser/renderer; TCP listeners у процессов
браузера не обнаружены. Во втором прогоне при восстановлении обычного
запуска pywinauto выбросил KeyError None в find_wrapper при перечислении
descendants. Свежая сессия затем успешно прочитала устройство; механизм
этой ошибки не установлен. Обычный запуск без флагов восстановлен,
Current 17.02.0501, idle, FlySafe-запрос обнаружен и оставлен открытым.
Прошивки не запускались. Через официальный launcher CDP доступ этим
способом не получен; превращать эксперимент в работающий JS-хук пока нельзя.

Дополнительный read-only поиск конфигурации DJIService не выявил настройки
аргументов браузера в проверенных config.xml, defaultsettings.ini,
qt.conf и dbus_pc.json. Эти файлы относятся к порогам питания,
доступности функций, путям Qt и USB-маршрутизации. В бинарнике сервиса
обнаружены импорты QProcess и фиксированные строки путей DJIBrowser;
это не доказывает отсутствие иных настроек, но поддерживаемый способ
передачи Chromium switches пока не найден. Неизвестные --debugger и
--test_server не запускались, USB/firmware-конфигурация не менялась.

## Отдельный Windows desktop: предварительный эксперимент

Пустое тестовое приложение на установленном Electron 0.36.7 успешно
запущено через Win32 CreateProcess с `STARTUPINFO.lpDesktop`,
указывающим на временный desktop в WinSta0. EnumDesktopWindows
подтвердил принадлежность окна Chrome_WidgetWin_1 этому desktop и PID
тестового процесса. Активный desktop не переключался; foreground window
и положение курсора до и после появления окна совпали. Приложение
штатно завершилось с кодом 0, handle desktop закрыт, временные файлы удалены.

Для этого использован `win32process.STARTUPINFO`: произвольное добавление
атрибута lpDesktop к `subprocess.STARTUPINFO` не передало его CreateProcess
и не обеспечило изоляцию. Запуск из MCP-контекста также завершался кодом 1
на обычном desktop; положительный тест выполнен из терминального контекста.

Следующие два live-прогона проверили и установленный DJI Assistant:

- Перед первым запуском подтверждены Current 17.02.0501 и idle.
  Обычный Assistant штатно закрыт; проверено завершение его процессов,
  чтобы не создавать второй frontend одновременно.
- Официальный launcher запущен через CreateProcess на временном desktop.
  Цепочка launcher/service/browser успешно открыла единственное окно.
  Отдельный Python worker на том же desktop подключился через UIA;
  SDK с `allow_physical_input=False, addressed_input=True` открыл
  Matrice 4T и прочитал Current 17.02.0501, idle.
- Во втором прогоне GetThreadDesktop подтвердил desktop основного окна
  браузера и принадлежащего ему native file picker: оба находились
  на созданном неактивном desktop, не на Default.
  Из свежего пустого поля SDK выбрал официальный
  `M4T_UAV_17.02.05.01_pro.zip` и прочитал полный путь обратно.
  Start Upgrade и Start Update не нажимались.
- Во время второго прогона OpenInputDesktop проверялся каждые 100 мс:
  активным оставался Default. Измеренные владельцы foreground window
  принадлежали explorer, Chrome, VS Code и другому пользовательскому
  приложению, не DJI. Фокус и курсор между начальным и конечным замерами
  менялись; причина этих изменений отдельно не установлена. Это не
  основание обещать неизменность пользовательского ввода или отсутствие
  кратковременных событий между замерами.
- После выбора ZIP снова подтверждены Current 17.02.0501 и idle.
  Оба изолированных прогона закончились штатным выходом Assistant;
  перечисление окон соответствующего desktop вернуло пустой список,
  worker завершился с кодом 0, handle desktop закрыт.
  Затем обычный запуск восстановлен: Current 17.02.0501, idle,
  FlySafe-предложение оставлено открытым, обновление базы не запускалось.

Таким образом, read-only навигация и offline-select на отдельном desktop
подтверждены на живом приложении. Изолированные firmware-write
операции не проверялись и этим экспериментом не разрешались. Установленные
файлы DJI не менялись, временный экспериментальный runner удален.
