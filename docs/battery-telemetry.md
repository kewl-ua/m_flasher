# Батарея: наблюдения и однократные DUML-запросы

[Главная и карта документации](../README.md)

Есть стабильное совпадение кандидата SOC с Pilot 2 при 35% и совпадение при переходе 34 -> 33%. Универсальный decoder и production battery API не подтверждены.

Материалы ниже сохраняют ход исследования. Последующие записи могут уточнять ранние гипотезы; ограничения приведены рядом с результатами.

## Сводка результатов

| Подход | Наблюдение | Граница вывода |
|---|---|---|
| Пассивный USB/frontend | Идентификация и OSD исследованы | Проверенный SOC не найден |
| Native checker и memory | Маршрут 0D/02 восстановлен; memory-кандидаты отвергнуты | Подробности в [native-анализе](./native-analysis.md) |
| Первый запрос 0D/02 | Контроль 38 -> 37%, фильтр exact C0, совпадение не найдено | Фильтр оказался слишком строгим; raw stream не сохранен |
| Второй запрос 0D/02 | Контроль 35 -> 35%, flags 80, result 00, payload 45, offset 21 = 35 | Положительная стабильная single-point проверка |
| Третий запрос 0D/02 | Контроль 34 -> 33%, offset 21 = 33 | Совпадает с последующим контролем, но не стабильная вторая точка |

## Пассивное исследование модели, идентификации и батареи

Следующий локальный захват 2026-10-04 снова ограничен только drone address
47 на USBPcap1; address перед началом повторно проверен через Windows hub.
Сценарий: штатный скрытый launch, open-device Matrice 4T, Current/status,
нормальный quit. Результат UI: **17.02.0501 / idle**. Собственных новых
команд DJI, claim или bulk I/O исследовательский код не выполнял.
Остановлены только два процесса захвата с нашим точным output path;
посторонние USBPcap-процессы не затронуты.

Локальный разбор: 8121 CRC-валидный пакет, все распознанные DUML packets
на endpoints OUT 04 / IN 85; 3431 нераспознанный байт и 9 байт хвостов
на других endpoint streams. Сопоставлены 2706 ответов с предыдущими
запросами по sequence, обратным адресам, command set / ID и response bit.
Это число сопоставлений, не гарантия уникальности или полноты capture.

| Данные | Наблюдаемые факты | Ограничение |
| --- | --- | --- |
| Семейство модели | `WA345T AC Ver.A` в 00/01 от 1F, `WA345T AC Ver.0` от 48; `WA345T` также встречается в 00/81, 00/82 и конфигурационных данных 00/4F | Это внутренние product/module labels; универсальное преобразование в название модели не подтверждено |
| Идентификация | Коррелируемая пара 00/51 к 68: request payload 04, response payload 27 байт, первый байт 00 и 20 печатных ASCII-байт с payload offset 7 | Кандидат serial/identification, значение не публикуется; принадлежность конкретному компоненту и совпадение с aircraft SN еще требуют отдельной проверки |
| Другой serial-запрос | 00/51 к 28: request payload 01, response payload только 1 байт D6 | Ответ нельзя выдавать за серийный номер или подменять значением от другого модуля; значение кода D6 неизвестно |
| Метаданные параметров | 03/E1 дал 907 записей table/index/name/type/size; 03/E2 дал значения для тех же 907 идентификаторов, сопоставленные с запросами | Имена и размеры проверяются по метаданным текущего устройства, индексы не считаются стабильным API |
| Батарея | Есть имена `battery_status`, `bat_debug_hide_percentage`, `soc_bat_remain_cap_percentage_display` и пороги батареи | Сами имена и настройки отображения не доказывают текущий процент заряда, напряжение, температуру или число циклов |

Важный отрицательный результат: 311 push-пакетов 03/43 (OSD General)
имеют payload **84 байта**. Публичный старый dissector рассчитан на
50/55 байт и помещает Battery Remain по offset 40. В нашем capture
этот байт в 191 из 311 пакетов превышает 100 и быстро меняется.
Такую раскладку нельзя применять к M4T: процент батареи не декодирован.
Product Type из старой схемы также не используется для определения модели.
Пакеты battery command set 0D и старый 04/06 в этом сценарии не наблюдались;
это не доказательство отсутствия их поддержки устройством.

Штатный запуск Assistant нельзя описывать как транспорт, отправляющий
исключительно read-команды: в capture есть одна пара 00/4A, которую
публичная таблица именует Set Date/Time, а семантика некоторых других
служебных команд не установлена. Собственный код лишь наблюдал этот обмен.
Команды 00/07-0B (loader/update/reboot в публичной таблице) среди
распознанных пакетов не обнаружены; операции прошивки не запускались.
Команды из capture не добавляются автоматически в allowlist и не
воспроизводятся только потому, что их использует официальный Assistant.

Следующая исследовательская граница для батареи — подтвержденная схема
M4T и независимое сравнение с отображением заряда, а не подбор удобного
байта в диапазоне 0-100. Для идентификации требуется локальная проверка
того, какому компоненту принадлежит ответ, без публикации SN.
Raw capture, извлеченные payloads и временный parser после анализа удалены;
публичный SDK/CLI на этом этапе не менялся. Assistant нормально закрыт.

Публичные имена команд и исторические схемы (не спецификация M4T):
[dji-dumlv1-general.lua](https://github.com/o-gs/dji-firmware-tools/blob/master/comm_dissector/wireshark/dji-dumlv1-general.lua),
[dji-dumlv1-flyc.lua](https://github.com/o-gs/dji-firmware-tools/blob/master/comm_dissector/wireshark/dji-dumlv1-flyc.lua),
[dji-dumlv1-proto.lua](https://github.com/o-gs/dji-firmware-tools/blob/master/comm_dissector/wireshark/dji-dumlv1-proto.lua).

## Проверка границ frontend API Assistant

Локальное read-only исследование установленного app.asar не дало готовой
схемы M4T battery telemetry, но позволило исключить два ложных пути.
Архив прочитан непосредственно, без распаковки на диск, изменений,
выполнения его JavaScript или отправки запросов native service.
SHA256 остался
`fd9cd1857b2fcec4ed19d71a189d7216390dfda606e8b08358843194ea76c28d`.

- Device routing содержит `Uav_wa345t`, внутренний id `wa345t` и переход
  в страницу m210 / upgrade-multi. Это согласуется с нашим живым маршрутом,
  но само по себе не определяет числовой product id в USB payload.
- `GetBatteryInfo` и `GetDynamicBatteryInfo` зарегистрированы frontend
  WebSocket wrapper в ветке `paramshow`, route `/controller/paramshow/`.
  Их consumer найден в отдельных страницах battery_charge_hub и
  charging-device. Там есть поля SOC, voltage, current и temperature.
  Наличие этих имен не доказывает поддержку данного API подключенным M4T;
  этот route не вызывался.
- `GetDeviceSN` и `GetControllerSN` зарегистрированы в другой ветке,
  `/controller/config/user/`. Поиск этих имен в build JavaScript нашел
  регистрацию в ws и consumer в m600, но не в m210. Это не доказательство
  отсутствия поддержки native service и не привязка USB ответа от 68
  к aircraft SN. Запросы этого API не выполнялись.

Таким образом, похожее название метода в общих файлах Assistant нельзя
принимать за проверенную функцию именно M4T. Подтверждение заряда требует
независимого отображения с той же установленной батареей (например,
DJI Pilot 2) и проверки схемы, а принадлежность SN — локального сравнения
с идентификатором конкретного компонента. Самостоятельные новые команды,
вызовы служебных WebSocket API и изменение настроек не выполнялись.

## Независимая сверка с DJI Pilot 2: 70%

Пользователь подтвердил **70%** на пульте до и после следующего короткого
захвата, без смены установленной батареи или USB-подключения.
Windows hub повторно подтвердил drone address 47. Сценарий Assistant:
скрытый launch, open-device, Current/status и нормальный quit.
Current остался **17.02.0501 / idle**; собственных новых DJI-команд не было.

Локально разобраны 8949 CRC-валидных пакетов; 4297 нераспознанных байт
учтены отдельно, полнота декодирования не заявляется. Среди них 378
OSD 03/43 payloads длиной 84 байта. Проверка всех смещений в этих payloads
не нашла постоянного значения 70 в виде uint8 или uint16 little-endian,
либо 0.70 в виде float32 little-endian (допуск 0.00001).
Постоянные uint8 значения 68/69 также не обнаружены.
Battery command set 0D в распознанном потоке отсутствовал.

Это ограниченный отрицательный результат, а не доказательство отсутствия
battery telemetry: значение может находиться в другом сообщении, иметь
другой формат, упаковку или семантику. Поиск числового совпадения не
подменяет спецификацию и независимую проверку. Процент заряда через USB
по-прежнему не декодирован; fake/default значение 70 не добавляется.
Для дальнейшей проверки сначала нужна обоснованная схема/кандидат поля,
затем сравнение на нескольких разных показаниях Pilot 2.
Специальная разрядка батареи и длительное удержание дрона включенным
для подбора смещений не выполнялись. Raw capture и извлеченные payloads
после анализа удалены; Assistant и наши capture-процессы завершены.

После естественного изменения заряда пользователь подтвердил **69%**
до и после второго короткого сценария. Его capture содержит 7103
CRC-валидных пакета, в том числе 193 OSD 03/43 payloads по 84 байта;
3299 нераспознанных байт и 9 байт хвостов учитываются отдельно.
В первом capture также было 9 байт хвостов.
Оба capture содержат только USB device address 47.

Сравнение двух OSD выборок не нашло uint8-смещения, постоянного внутри
каждой выборки и изменившегося между ними. Не найдено и постоянного
7/8-битного поля внутри одного байта, которое соответствовало бы
70 и 69 соответственно; постоянного uint8 69 во второй выборке нет.
Это проверяет лишь перечисленные простые представления, а не исключает
другие форматы или другие сообщения. Battery command set 0D снова
не наблюдался. Дополнительный ориентир пользователя: компас показывал
244, затем 286; эти показания не являются синхронизированной временной
серией и не используются для декодирования yaw или выбора поля батареи.

Оба сценария завершились нормальным quit Assistant с Current
17.02.0501 / idle. Все четыре временных файла (два raw capture и два
извлечения payloads) удалены. До появления обоснованного кандидата поля
новые показания заряда сами по себе не обосновывают декодер;
специально разряжать или поворачивать дрон не требуется.
Позднейший ориентир пользователя — 68%; нового capture для этого
показания не выполнялось, поэтому его нельзя считать третьей
синхронизированной выборкой.

## Однократный экспериментальный battery DUML query

2026-10-04 пользователь отдельно разрешил один запрос 0D/02,
без повторов/перебора, подтвердив ground state, выключенные моторы
и отсутствие обновления. Перед запросом Pilot 2 показывал 38%;
последующий пользовательский tick — 37%, поэтому стабильное
контрольное значение за весь интервал не заявляется.
DJI-процессы были закрыты. Session-only probe проверил fingerprint
64-bit DLL, ABI, host metadata mapping к MI04, configuration
descriptor и endpoints 04/85. Offline CRC vectors, fragmented
stream parsing и request shape прошли до USB вызовов.

Отправлен один 17-байтовый пакет: 2A -> 0B, command 0D/02,
payload `00 00 01 05`, sequence 0x9EB5. Bulk write вернул 17.
За ограниченное пятисекундное ожидание прочитано 204410 байт,
распознано 3368 CRC-valid пакетов вне точного response key
(обратные адреса, тот же sequence, flags C0, command 0D/02).
Совпадающего ответа не найдено. Полнота stream decoding не
заявляется; это не доказательство отсутствия поддержки команды,
не отказ устройства с известным error code и не измерение SOC.
Raw traffic/payloads не сохранялись; только итоговые счетчики.

Последующая статическая проверка выявила ограничение нашего response
filter: требование точного flags C0 было слишком строгим.
Serializer 0x79FCE0 очищает header, формирует bits 5/6 из internal
command type, отдельно устанавливает bit 7 для type 4
(0x79FDB1--0x79FDC3) и low nibble из object +0x30
(0x79FDD2--0x79FDDB). Decoder 0x79FF90 отдельно извлекает
bits 5/6 (0x7A0067/0x7A006D) и low nibble (0x7A007F).
Поэтому C0 нельзя считать универсальным response byte на основании
одного ранее полученного version ответа. Предыдущий результат означает
только отсутствие совпадения с точным C0 filter; возможный ответ
с другими flags не исключен. Raw stream уже не сохранен, так что
ретроспективно проверить его нельзя.

Session probe исправлен: envelope correlation сохраняет reversed
addresses, sequence, command и response bit 7, но не требует полного
совпадения flags. Low nibble сохраняется отдельно; при ненулевом
значении payload не интерпретируется как plain result/SOC.
Offline проверки CRC-valid искусственных вариантов 80/A0/C0/E0/83
и отрицательных случаев request bit, других адресов, sequence и
command прошли. Это тест probe, не live подтверждение поддержки
всех вариантов M4T и не полная реконструкция native matcher.
Новой отправки не было; назначение receiver 0B остается непроверенным.

Повторной отправки, reset, set_configuration, set_altinterface,
вызова native Assistant методов или firmware операций не было.
Interface освобожден, native handle закрыт; последующая Windows
проверка показала MI04 status OK и отсутствие DJI-процессов.
Эксперимент не подтвердил battery query для M4T; SDK decoder
и публичный CLI не изменены.

## Ответ battery query с исправленным фильтром: контроль 35%

Пользователь отдельно разрешил одну новую отправку той же команды
при прежних ground/motors-off/no-upgrade условиях. Первый record
сохранен; новый session record и exclusive creation gate исключают
автоматическое повторение этой попытки. Pilot 2 показывал **35%**
до запроса и, по последующему подтверждению пользователя, после него.
Fingerprint/ABI, отсутствие DJI-процессов, host mapping MI04 и
configuration descriptor проверены заново; offline tests прошли.

Один запрос 2A -> 0B, 0D/02, payload `00 00 01 05`,
sequence **0x0D8C** полностью отправлен (bulk write 17).
Получен CRC8/CRC16-valid ответ с обратными адресами, тем же sequence
и командой; **flags 80**, encoding nibble 0, result byte **00**,
payload length **45**. Кандидат raw payload offset 21 равен **35**,
что совпало со стабильным независимым показанием Pilot 2.
Это первая положительная single-point проверка найденного кандидата
на данном M4T. Она не доказывает полную схему ответа, универсальность
SOC offset или назначение всех остальных полей/receiver 0B.
Flags 80 также подтверждают, что прежний exact C0 filter был
непригоден для этого ответа; наличие ответа в первой попытке
ретроспективно установить нельзя.

До остановки чтения получено 199421 байт; распознано 3277 других
CRC-valid пакетов и один пакет 0D/02, совпавший с sequence.
Raw traffic и полный payload не сохранялись, только итоговые
счетчики и кандидат. Interface освобожден, handle закрыт,
Windows MI04 status OK; DJI-процессы отсутствовали после обмена.
Повторной отправки в этой попытке, смены configuration/altinterface,
reset или firmware действий не было. Production SDK/CLI не изменен;
перед decoder нужна независимая проверка при другом естественном
показании заряда с отдельным разрешением на новый запрос.

## Третий battery query: переход 34 -> 33%

Следующая отдельно разрешенная однократная проверка имела контроль
Pilot 2 **34% до отправки**. Новый record сохранен отдельно, без
перезаписи предыдущих попыток. Fingerprint/ABI, closed-process guard,
host mapping MI04, descriptor и offline tests снова прошли.
Один запрос с sequence **0xA0ED** полностью отправлен (17 байт);
CRC-valid коррелируемый ответ имеет flags 80, encoding nibble 0,
result 00 и payload 45 байт. Raw offset 21 равен **33**.
После запроса пользователь подтвердил, что Pilot 2 переключился
на **33%**. Это согласуется с естественным изменением заряда, но
не является второй стабильной before/after точкой: точное время
перехода относительно ответа не установлено.
Прочитано 39715 байт, распознано 654 других CRC-valid пакета
и один совпадающий 0D/02. Interface освобожден, handle закрыт,
MI04 status OK, DJI-процессы отсутствовали. Повторов и изменений
configuration не было. Теперь имеются стабильное совпадение при 35%
и совпадение с последующим контролем 33% во время перехода 34 -> 33;
это не основание заявлять точность/универсальность SOC decoder.
